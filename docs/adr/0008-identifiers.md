# 0008. Identifiers: UUIDv7 and strongly typed ids

- **Status:** Accepted
- **Date:** 2026-10-12

## Context

A transfer's id is its idempotency key towards the Ledger ([ADR 0003](0003-modular-monolith-with-ledger-as-posting-engine.md)), so it must exist before anything is saved, and the domain is built before there is a database. Ids also appear in URLs, where guessable values invite enumeration attacks (IDOR). Ledger code takes many id parameters, and passing the wrong one compiles silently when they are all `Guid`.

## Decision

- Technical ids are **UUIDv7**, generated by the application with `Guid.CreateVersion7()`.
- Each aggregate has a **strongly typed id**: `readonly record struct AccountId(Guid Value)`, `JournalEntryId`, `TransferId`.
- A module refers to another module's entities with the **plain `Guid`** that the other module's Contracts expose, because it may not reference that module's Domain. Transfers stores `SourceAccountId` as a `Guid`.
- Business identifiers that customers see (IBAN, account number) are separate fields, never primary keys.

## Alternatives considered

- **Database identity (`bigint`):** compact and fast, but unknown until the row is inserted, and sequential values are guessable.
- **UUIDv4:** random, so every insert lands in a random place of the primary key's B-tree and splits pages. UUIDv7 starts with a timestamp, so inserts append like a sequence. PostgreSQL 18 can also generate it with `uuidv7()`.
- **Plain `Guid` everywhere:** less code, but a call with swapped `TransferId` and `AccountId` arguments compiles.

## Consequences

- The compiler catches mixed-up id types. It does not catch two ids of the same type swapped, such as source and destination, nor the plain `Guid` ids that cross module boundaries.
- Persistence and JSON need converters for the typed ids (phase 2).
- `default(AccountId)` is `Guid.Empty`; code must not rely on it.
